# Feature: associate-renewal

**Status:** Done
**Repos affected:** association_management_BE, association-management-frontend

## Spec (analyst)

**Problem:**

Today the only way to register someone as an `Associate` for a year is `CreateAssociate.vue` (`src/views/CreateAssociate.vue`), reached via the "+ New Associate" button on `Associates.vue` (`src/views/Associates.vue`). That form always asks for the full ~13-field identity dataset (name, fiscal code, address, birth date, etc.) and, for minors, a full parent-relation sub-form — every time, even for a person who is already a fully-registered `User` from a prior year. There is no "renew this person for `<year>`" shortcut anywhere in the app.

This feature removes that combined flow and replaces it with two purpose-built flows that match the actual domain shape (per the top-level `CLAUDE.md`: a `User` is a person registry row, an `Associate` is one yearly membership for that `User`): a new "Add User" entry point on `Users.vue` for registering a brand-new person (identity data only, no associate/year), and a new "Associate for `<year>`" action on `UserDetail.vue` for giving an *already-registered* `User` a new yearly `Associate` record (just the year, nothing else).

Backend companion spec: `docs/features/associate-renewal.md` in `association_management_BE` (new standalone user-creation endpoint, new minimal associate-creation endpoint, new paginated associate-history endpoint, removal of the combined `POST /associate` flow).

**Scope:**

1. **Remove the "Create Associate" flow entirely.** Delete `src/views/CreateAssociate.vue`, its route (`{ path: '/associates/create', name: 'CreateAssociate', ... }` in `src/router.js`), and the "+ New Associate" button on `Associates.vue` (`goToCreateAssociate`, the `<button @click="goToCreateAssociate">` in the template, and the `showCreatedMessage`/`created=1`-query-param success-banner logic tied to the old create flow, since nothing will redirect there with that query param anymore). `Associates.vue` is otherwise **untouched** — it keeps listing/managing existing yearly `Associate` records (courses, payments, etc.) via `AssociatesFilteredTable.vue` → `/associates/:id/manage` exactly as today.

2. **New "Add User" entry point on `Users.vue`.** A button (e.g. "+ Add User", mirroring the now-deleted "+ New Associate" button's placement/styling convention) opens a form with the 13 identity-only fields — `name, lastName, email, secondaryEmail, fiscalCode, birthDate, birthCity, identityCardNumber, residenceAddress, residenceCity, residenceCAP, residenceProvince, phoneNumber` (same set `CreateAssociate.vue`'s "Associate Data" section collects today, and the same set `UserDetail.vue`'s edit-user-data feature already treats as the canonical editable-field list). If the entered `birthDate` makes the person a minor, an adult-relation sub-section appears and is required — this directly mirrors `CreateAssociate.vue`'s existing `isMinor`/"Parent Relation (Required for minors)" section (same field set, same `isAdult`/`isMinor` age-calculation logic), just relocated to this new form. Calls the backend's new standalone user-creation endpoint (see BE spec).

3. **`UserDetail.vue` (`src/views/UserDetail.vue`) gains three things:**
   - A current-year associate-status indicator: "Associated for `<year>`: yes/no", where `<year>` defaults to the current calendar year (`new Date().getFullYear()`, same default `CreateAssociate.vue` uses today for `validityYearStart`) and is editable.
   - An **"Associate for `<year>`"** button/CTA next to that indicator. The year field is the *only* input this action asks for — no discount, no relations, no courses. The button is disabled/hidden whenever an `Associate` already exists for that user+year (requires knowing, for the currently-selected year, whether one exists — see open question below on how that's determined without over-fetching). Calls the backend's new minimal associate-creation endpoint (see BE spec). After a successful call, courses and fee payment continue to be added via the existing, **unmodified** `AssociateManage.vue` flow (add-course modal, mark-fee-paid modal) — the natural next step is presumably navigating to `/associates/:id/manage` for the newly-created associate, using the `id` the create call returns.
   - A **"View Association History"** button opening a paginated modal listing that user's past/current associate years (sourced from the backend's new `GET /user/<pk>/associates`-style endpoint), paginated the same way `Users.vue`/`Associates.vue` already paginate their list tables.

4. **Extract a shared `usePagination` composable** and retrofit existing pagination call sites to use it, per Andrea's explicit instruction that this extraction is part of this feature (the new History modal would otherwise be a fresh duplicate of the same Previous/Page-X-of-Y/Next widget logic).

**Grounding correction on item 4's scope (found while reading the actual code, not assumed from the brainstorm):** a direct grep for the pagination widget's signature methods (`totalPages`, `goToNextPage`, `goToPreviousPage`, `hasNextPage`, `hasPreviousPage`, `pagination-btn`) across `src/` turns up **only two** existing files: `src/components/AssociatesFilteredTable.vue` and `src/components/UsersFilteredTable.vue`. `src/views/Courses.vue` has no pagination at all today — it fetches and client-side-sorts the full course list with no page controls or `itemsPerPage`/`totalCount` props. `src/views/AssociateManage.vue`'s courses table (the per-associate course list) likewise has no pagination — it renders `associate.courses` in full, unpaginated (consistent with course-per-associate counts being small). So the "4 duplicate call sites" framing from the brainstorm appears to overstate the current duplication: there are 2 existing call sites today, and this feature's new History modal would be a 3rd. The `usePagination` extraction itself is still worth doing (even 2 near-identical copies plus a 3rd new one is enough duplication to justify it, and Andrea explicitly asked for it), but "retrofit all of those existing call sites" should mean `AssociatesFilteredTable.vue` and `UsersFilteredTable.vue` only — there is no existing pagination logic in `Courses.vue` or `AssociateManage.vue` to retrofit. Flagged as an open question below so Andrea can confirm before the architect scopes the extraction.

**5. Clear on-screen error for the two new creation flows; backend logging handled server-side.** Per Andrea's explicit requirement: when "Add User" or "Associate for `<year>`" fails, Erica needs to see a clear, specific error (not a generic "something went wrong"). The backend half of "so Andrea can diagnose it without watching her screen" is handled entirely server-side (see BE spec #5 — the two new views log their own failures inline) — **no frontend reporting call, no new service, no reference code.** (Revised 2026-11-06: the original design here had the frontend generate a reference code and POST it to a new BE endpoint; dropped because that second network call would most likely fail for the same reason the first one did, e.g. the network being down, so it added real plumbing for little actual coverage over just logging server-side.)
- On failure of either creation call, show the actual status/message from the response in the on-screen error (mirroring the level of detail `CreateAssociate.vue`'s existing `error-container`/`error-message` already shows today) — specific enough that Erica can read it to Andrea, who can then find the matching log line by timestamp/action without needing a manufactured code.
- Scoped to just these two new flows for now — not a retrofit of every existing `console.error` call site in the app (see the extensive existing list of console-only error handling across `useUsers.js`, `useAssociates.js`, `Associates.vue`, `Courses.vue`, etc.). Extending this pattern elsewhere is a separate future task, not part of this feature.

- **No changes to `association_management_devops`.**

**Open questions (for the architect):**

1. **How does `UserDetail.vue` know, for an arbitrary editable `<year>`, whether an `Associate` already exists for that user+year, without over-fetching?** Three options surfaced while grounding this spec: (a) the new paginated history endpoint's results already contain every year an associate exists for this user — the frontend could derive "does `<year>` exist" from an already-fetched/cached history list rather than a separate check, at the cost of needing the full (or at least first-page) history loaded before the indicator/button can render correctly; (b) a dedicated lightweight existence-check call (e.g. hitting the BE's new minimal-create endpoint's underlying query without mutating, if such a read path is exposed); (c) simply attempt the create and handle the "already exists" 4xx as the disable signal after the fact (optimistic, simplest, but means the button isn't correctly disabled *before* a user clicks it for an already-existing year — likely not acceptable UX given Andrea's explicit requirement that the CTA be "disabled/hidden when an Associate already exists"). Leaning toward (a), but flagging since it has a real UX/performance tradeoff (loading history eagerly just to compute a yes/no flag) that the architect should decide deliberately, not by default.
2. **Does `usersService`/`useUserManage.js` grow a single combined "create user" method that also submits relations in one request (matching the BE's single endpoint, per the BE spec's scope #2), or does the frontend's "Add User" form need two calls (create user, then create relation(s))?** This mirrors the BE spec's own open question #3/#4 about whether the relations array survives in the new endpoint's request shape — the frontend composable/service shape should match whatever the BE architect decides there, so this is flagged here as a dependency rather than resolved independently.

## Architecture (architect)

### Resolving the 2 remaining open questions

**1. How `UserDetail.vue` determines whether an `Associate` already exists for an arbitrary editable `<year>`: option (a), with a correctness argument for why eager-loading is actually safe here, not just "good enough."**

The backend's `GET /user/<pk>/associates` (see `association_management_BE`'s architecture doc) is capped at `max_page_size=100`. `Associate.validityYearStart` has a hard floor of `2025` (`MinValueValidator(2025)` on the model) and the model's own `UniqueConstraint` guarantees at most one `Associate` row per `(user, validityYearStart, validityYearEnd)` — so a single user can never have more than `(current_year − 2025 + 1)` rows, a number that will not reach 100 for a very long time (decades). That means fetching that endpoint once with `limit=100` is not "probably enough," it is **provably a complete fetch of this user's entire association history**, for the realistic lifetime of this app.

Given that, `UserDetail.vue` fetches the user's full association history **once, on mount** (`fetchAssociateHistory(userId, { limit: 100 })`, see composable below), not lazily when the History modal opens. This single extra request per detail-page visit powers both:
- the "Associated for `<year>`" yes/no indicator — derived client-side as `associateHistory.value.some(a => a.validityYearStart === selectedYear.value)`, recomputed instantly whenever the editable `<year>` field changes, no extra network round-trip per year edit;
- the "View Association History" modal's content (see below) — reusing the exact same already-loaded array rather than re-fetching when the modal opens.

This explicitly rejects option (b) (a dedicated existence-check endpoint) because the BE architecture doc deliberately does not introduce one — the BE's minimal associate-create endpoint has no side-channel read path, and adding one just for this would be new BE surface area for a question the history endpoint already answers for free. It rejects option (c) (optimistic create-and-handle-409) because Andrea's explicit requirement is that the CTA be disabled/hidden *before* a click, not merely safe from a race.

**2. "Add User" is a single combined API call, matching the BE's single `POST /user` endpoint (which accepts an optional `relations` array in the same request body — see the BE architecture doc's resolution of its own open questions #3/#4).** There is no separate "create relation" call from the frontend at any point — `usersService.createUser(payload)` sends the 13 identity fields plus (for a minor) a `relations` array in one request, and the backend creates the `User` and every submitted `UserRelation` atomically in one transaction. This directly mirrors how `CreateAssociate.vue`'s old `submitAssociate` already built a single payload with a nested `relations` array for the old combined endpoint — the "Add User" page's `buildPayload()`-equivalent is structurally the same shape, just without the `validityYearStart/End`/`associate` wrapper key (the new endpoint's identity fields are top-level, not nested under `associate`).

### Services

**`src/services/associatesService.js`** — `createAssociate(payload)` is **kept under the same method name**, but its payload shape and meaning change completely, mirroring the BE architecture doc's decision to reuse the `POST /associate` route/class names for an unrelated, minimal body:
```js
async createAssociate({ userId, validityYearStart }) {
  // POST /associate  →  { userId, validityYearStart }
  // response: { id, validityYearStart, validityYearEnd, annualFeePaid }
}
```
The old 13-field-plus-relations payload this method used to send is gone along with `CreateAssociate.vue`, its only caller. No other method on this service changes.

**`src/services/usersService.js`** gains two new methods, same try/catch-log-rethrow shape as the existing ones:
```js
async createUser(payload) {
  // POST /user  →  { name, lastName, email, secondaryEmail, fiscalCode, birthDate,
  //                   birthCity, identityCardNumber, residenceAddress, residenceCity,
  //                   residenceCAP, residenceProvince, phoneNumber, relations?: [...] }
  // response: full UserDetailSerializer shape (same as getUser(id)'s response),
  //   status 201 if newly created, 200 if fiscalCode already matched an existing User
  //   (no fields modified) — the only service method whose caller needs the status
  //   code itself, not just the body, per Andrea's existing-user requirement.
},
async getAssociateHistory(userId, { page, limit } = {}) {
  // GET /user/:id/associates?page=&limit=
  // response: standard DRF pagination envelope { count, next, previous, results }
  //   results: [{ id, validityYearStart, validityYearEnd, annualFeePaid }]
}
```

**~~`src/services/errorReportingService.js`~~ — dropped (2026-11-06), no new service file.** The original design here had this call a new `POST /client-error` endpoint; both the endpoint and this service are gone (see spec scope #5 and the BE architecture doc's superseded #5) — the backend now logs these failures itself, inline in the two views that produce them.

### Composables

**`src/composables/usePagination.js`** (new — extracted from the duplicated widget logic in `AssociatesFilteredTable.vue`/`UsersFilteredTable.vue`):
- Input: reactive `totalCount` and `itemsPerPage` (numbers or refs/computed), plus an initial `currentPage`.
- Output: `currentPage` (ref), `totalPages`, `hasNextPage`, `hasPreviousPage` (computed), `goToNextPage(onChange)`, `goToPreviousPage(onChange)` — the two navigation methods take an optional callback invoked with the new page number *after* `currentPage` is updated internally, letting the calling component decide what "a page changed" means.
- This last detail is deliberate: for `AssociatesFilteredTable.vue`/`UsersFilteredTable.vue`, `onChange` is `(page) => emit('page-change', page)` — **unchanged behavior**, same prop/emit contract the parent views (`Associates.vue`/`Users.vue`) already rely on, satisfying the acceptance criterion that the extraction causes no regression there. For the new History modal (below), `onChange` instead re-slices the already-fully-loaded 100-item `associateHistory` array client-side — no network call on page-change, since (per open question 1's resolution above) that array is already guaranteed complete. The composable itself stays agnostic to which of those two things the caller does with the callback; it only owns the page-arithmetic, exactly the part that was actually duplicated before.

**`src/composables/useUserManage.js`** gains (alongside its existing `user`/`relations`/`updateUser` state, all unchanged):
- `creating` / `createError` (refs) + `createUser(payload)`: calls `usersService.createUser(payload)`; on success returns `{ user, created }` (`user` in the same shape `fetchUser` already produces, `created` the boolean derived from the response's `201`/`200` status) without mutating `user`/`relations` state (this method is used by the standalone `AddUser.vue` page, which has no existing user loaded — it's a fresh composable instance per page visit, same as today's pattern of instantiating `useUserManage()` fresh per view). On failure, sets `createError` to the DRF field-error object (same `err.response?.data` convention `updateError` already uses) and returns `null`.
- `associateCreating` / `associateCreateError` (refs) + `createAssociateForUser(userId, validityYearStart)`: calls `associatesService.createAssociate({ userId, validityYearStart })`; on success appends the returned `{id, validityYearStart, validityYearEnd, annualFeePaid}` row to the front of `associateHistory` (so the indicator and modal reflect the new row immediately, without needing a refetch) and returns it; on a `409` specifically, sets a clean "An associate already exists for this year" message (reading `err.response?.data?.error`) rather than a generic failure string, since the backend's 409 path returns a purpose-built message for exactly this case; on any other failure, falls back to the generic `err.response?.data` / `err.message` convention used elsewhere.
- `associateHistory` (ref array, default `[]`), `associateHistoryTotalCount`, `associateHistoryLoading`, `associateHistoryError` + `fetchAssociateHistory(userId, { page, limit } = {})`: calls `usersService.getAssociateHistory(userId, { page, limit })`, following the same `runFetch`-style loading/error/data pattern already used by `fetchUser`/`fetchUserRelations` in this file. `UserDetail.vue` calls this once on mount with `{ limit: 100 }` (see open question 1's resolution) and stores the result as the single source of truth for both the indicator and the modal.
- Nothing is added to `useAssociateManage.js` or `useAssociates.js` — both stay untouched, per the Non-goals.

### Components / Views

**`src/views/CreateAssociate.vue`** — deleted in full.

**`src/views/Associates.vue`** — loses the "+ New Associate" button, `goToCreateAssociate`, and the `created=1`-query-param success-banner block; everything else (table, filters, pagination, "Manage" navigation) is untouched.

**`src/views/Users.vue`** — gains a "+ Add User" button next to the page header (mirroring the removed button's placement/styling on `Associates.vue`), wired to `router.push('/users/create')`. No composable/service change needed on this view itself — the button is pure navigation.

**`src/views/AddUser.vue`** (new, dedicated page per Andrea's resolved decision):
- Structurally a close relative of the deleted `CreateAssociate.vue`, minus the "Validity Year" section and the top-level `associate`/`parent` wrapper keys: the same 13-field identity form, the same `isMinor`/`isAdult` age-calculation logic (`calculateAge`, computed `associateAge`/`isMinor`/`isAdult`, the required-field red-outline/error-message pattern via `showRequiredError`) **relocated verbatim**, not reinvented, into this new file's `<script setup>`.
- Conditionally renders the "Parent Relation (Required for minors)" section exactly as `CreateAssociate.vue` does today, same fields, same `relationType: 'parent'` badge.
- `buildPayload()` produces the new top-level shape (no `validityYearStart/End`, no `associate` wrapper key — the identity fields sit directly at the payload root) plus the same conditional `relations: [{ user: {...}, relationType: 'parent' }]` array for minors.
- **On submit: calls `useUserManage().createUser(payload)`, which surfaces the backend's `201`-vs-`200` distinction (per the BE architecture doc's fix for Andrea's requirement that Erica be told when a submission didn't actually create anything).** `usersService.createUser`'s Axios call resolves with the response status alongside the body (`{ data, status }`, not just `data`, for this one method — every other service method on this file can keep returning bare `data` since nothing else depends on the status code); `useUserManage().createUser` returns `{ user, created }` as described above. `AddUser.vue` branches on `created`:
  - `created === true`: normal success — navigate to `/users/${user.id}`.
  - `created === false`: show a distinct, explicit banner **before** navigating — "A user with this fiscal code already exists — no changes were made to their record." — then navigate to that same existing user's `/users/${user.id}` (the response body is that existing user either way, so the id is always available). This is not an error state (no `reportClientError` call), it's a successful no-op clearly communicated, per Andrea's explicit "let Erica know this, saying that no data has been changed."
  - Either way, navigation happens — the distinction is only about *what Erica is told*, not about where she ends up, since in both cases there is now exactly one `User` row matching what she submitted and she should see its profile.
- On failure (4xx/5xx, not the 200/201 case above): shows the on-screen error (actual status/message, mirroring `CreateAssociate.vue`'s existing `error-container`/`error-message`) — no reference code, no reporting call; the backend's own inline logging (BE spec #5) covers the "Andrea can find out what happened" need. This specifically includes the new `400` a minor-without-adult-relation submission can trigger (the "Add User" form's own client-side check should normally catch this before submit, so hitting this server-side is the same kind of rare race/edge case as the associate-create `409` — still needs a clean error path, not a crash).

**Deviations from spec:**

Three real gaps/bugs were found and fixed during the tester-verification and `/code-review` passes after the initial green implementation — none of these were in the original Architecture section, all are additive fixes rather than scope changes:

1. **`UserDetail.vue` didn't surface `associateHistoryLoading`/`associateHistoryError` from the composable.** The architecture doc specified `fetchAssociateHistory` with its own loading/error state in `useUserManage.js`, but the initial implementation of `UserDetail.vue` never rendered those two refs — a failed history fetch silently fell through to the default "No" indicator with an enabled CTA instead of a loading or retryable-error state. Fixed by adding a loading block and a retryable-error block to the associate-status card (confirmed present in the shipped `UserDetail.vue`: the `associateHistoryLoading`/`associateHistoryError` blocks and `retryFetchAssociateHistory`), mirroring the existing pattern already used by the Relations card's own loading/error blocks.
2. **`AssociationHistoryModal.vue`'s `displayedHistory` was a plain `ref`, not reactive to the `history` prop.** The architecture doc's description of the modal implied the usual props-driven re-slice, but the first implementation captured `props.history.slice(...)` once into a plain ref at setup time. Because `UserDetail.vue` mounts the modal before its async `fetchAssociateHistory()` resolves (and later prepends a newly-created row to the same array on a successful "Associate for `<year>`" call), the modal showed correct pagination counts ("Page 1 of 2") but stale/empty rows until a manual Next click. Fixed by making `displayedHistory` a `computed` derived from `currentPage`/`props.history`/`props.itemsPerPage` — confirmed in the shipped file, with an inline comment explaining why a ref was wrong here.
3. **`AddUser.vue`'s error renderer didn't handle nested DRF relation errors.** The architecture doc's error-handling description (mirroring `CreateAssociate.vue`'s flat `error-container`/`error-message`) only anticipated a flat `{field: [messages]}` shape; a nested relation validation error (e.g. `{relations: [{user: {birthDate: [...]}}]}`, which the backend's `relations` array makes reachable) rendered as the literal text "[object Object]". Fixed with the recursive `firstErrorMessage` helper confirmed present in the shipped `AddUser.vue`, which descends into nested objects/arrays to find the first real string message.

No known accepted gaps remain on the frontend side as of hand-off (unlike the backend doc for this feature, which documents one).
